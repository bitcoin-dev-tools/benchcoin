## 1. Goal

Three ideas went in. From sipa's post in the libbitcoin thread: a missing input is an obligation to settle later, not a failure, so applying blocks stops being a total order. From libbitcoin: validation split from confirmation, only confirmation ordered. From Hornet and the research's section 9.5: a store written by age at a steady rate, with nothing emptied, and a compact entry. The window, deferral by prefix and the status flip deliver the first two and the oracle tests pin them; the third was delivered in mechanism at first and in effect only through the work of sections 4.4 and 4.8.

Ruling of the maintainer (2026-11-13): the series exists to remove every limitation on the validation side that does not scale with more hardware, so that the p2p part can then be optimised freely. Lines of code are not a criterion against it. That the connect outruns the delivery on a real sync is the intended result; the master reindex figure is of interest but decides nothing. The yardstick for each component is whether it removes or leaves a non-scaling limit in validation.

Phases: speed work on the connect; then, on the maintainer's word, consolidation and low-resource defaults (tuning instrumentation removed); the connect work paused at the 17:39 run and the receive side taken up; the design review of 2026-11-13 (sections 2, 4.1, 5, 7.6).

The current cut (2026-11-18): the port re-cut into 22 commits on master e211dd0186 (tip 74e8e1db9a, same tree as before the re-cut; backup `utxo-partial-order-before-recut`); the list is in 9.4, the gates in `/work/parallel-validation/consolidation-plan.md` section 8.

## 2. Constraints, each with its state

The text is the plan's section 1 (stage references left out), the state is the design review's, read at 10588 lines over 72 files and carried forward to the tip.

- **Consensus results identical.** Holds. Shown by the two store oracles against an in-order reference (`random_order_window_matches_in_order`, `same_as_cache_under_random_operations`), the fuzz target `coinsstore_window`, `validation_core_tests` and the unchanged functional suite; `src/consensus` and `src/script` are untouched. The one recorded gap (BIP30, 4.6) is closed. Open: the fuzz target does not reach the shard's own table or the depot and never gives the mark flag.
- **Crash safety equal to master.** Shown in part: `feature_async_undo` aborts before the first undo write, `feature_coins_lag` aborts inside write-out runs with reorgs mixed in and warns itself that the hook may not fire. Never exercised: crash recovery under load, a crash of a pruned node.
- **C1, the four architecture goals.** Pure validation functions (the core reads only its arguments and the view: no member, global, clock, log, file or lock); pure state machines (named transitions, asserted phases); asynchronous I/O (every write and sync is an effect on an executor, never under a validation lock); a radical reduction of `cs_main` scope. Oracles: `validation_core_tests` running the core with no `TestingSetup`, the `StagedConnect` phase assertions, the thread-safety annotations on a clang build. State: partly. Purity amended 15 November (the maintainer, "fine for now"): the core reads nothing of the node's (no member, global, file or lock; policy and time through BlockValidationContext); logging is allowed in the core and the consensus functions (amended 15 November, round 11 X7/V4, the maintainer: "Logging in the consensus functions is obviously fine!"; e.g. master's LogError lines in the free DisconnectBlock), and the one other exception is master's bench timing, a steady-clock read moved with the code it times; the purity script is dropped as an oracle. "No I/O under a validation lock" has one exception left: the per-acceptance `FlushStateToDisk` under cs_main that waits for the effects thread (4.7), since commit 15 (the pruning waits) only when pruning takes files (the prune event's block-index write and unlink stay under the lock, as in master); the full write once forced before the first disconnect of a reorg is gone since 14 November (4.4).
- **C2, default architecture, no new IBD mode.** No hints, no second validation path, no per-mode configuration. The window and the lag are run-time policies of one code path: the window is one when one block is available and larger when blocks are queued; the lag follows the memory budget. `-connectwindow=1` was meant as the same code with the window pinned; in the code it takes the serial path (`use_window` requires `ConnectWindow() > 1`). Known deviation, kept on the maintainer's word (15 November, round 11 X1/W1/T1/V1): the window, the receive hand-off and the request rule are chosen by `IsInitialBlockDownload()`, against this constraint and C17; a node that falls behind after the latch catches up serially; the historical chainstate connecting serially is wanted (it leaves the pool and memory to the active chain). Candidate for later (B): the active chainstate takes the window when more than one block is ready, the historical chainstate stays serial; it needs a catch-up functional test with a live mempool, an IBD re-measurement, and C17's reading written down (its text forbids asking whether a block is the only one in flight). C (the window always, also for one tip block) belongs to 5.2a. Also accepted (15 November, round 12 X2): outside initial block download each block's undo write and completions are awaited under cs_main, as master writes undo synchronously in ConnectBlock; inside it they stay asynchronous. The wait is kept for notification order (BlockConnected and UpdatedBlockTip leave with the block, announcements by headers, a transaction announced after the block it builds on), which does not matter in initial block download; no code change. Added later by the maintainer: no further special-case rules for when the window opens. State: holds. Two new options, `-blockcache` and `-connectwindow`; `-prevoutfetchthreads` sizes the connect pool.
- **C3, the tip as fast or faster than today, with everything the tip already has.** The block at the tip is reconstructed from the mempool through compact blocks, its transactions arrive hashed, its inputs are warm, and its scripts are mostly not run because the script execution and signature caches hold the mempool's verification. Each must survive: no re-hashing of reconstructed transactions, a store whose lookups warm the coins the mempool touches, the `ValidationCache` passed into the core unchanged, parallel prevout fetching for cold inputs. At a window of one nothing is deferred and a missing coin fails as today. Oracles: a `ConnectBlock` bench on a mainnet block with prevouts in a warm store and scripts off, and a regtest bench that accepts a block's transactions into a mempool first and then connects the block; both against master. State: the tip bench through the store exists since 15 November (ConnectBlockMainnetTipStore against TipOverlay, 5.2a): the store's round trip 1.14x master's shape, Confirm() the difference; the regtest mempool bench has no figure at a recent tip.
- **C4, low memory and few cores.** IBD must work on a node with 4 GB of RAM and a system-on-chip CPU. Every in-memory structure has a budget and the budgets sum to one stated figure. (The plan's "worker default not from the core count" is superseded by one thread a core, 4.9.) State: open, see 7.6; the byte budget per structure does not exist as one table.
- **C5, ultraprune.** Nothing requires a block older than the prune depth: a pruned node prunes only below the written head (the lag cap is gone, amended 15 November, 5.7), so a replay after a crash reads only kept blocks, pruning never removes a file inside the lag, and undo writes are settled before a block file is pruned. The stored UTXO set never exceeds what a client running today's code has at the same height: what is on disk is a subset of the set at the lag's lower head, with no history beside it; the write-out may issue an erase for a coin that was never written (accepted, 5.5), which leaves nothing on disk. At shutdown the lag is drained so the stored set is exactly the tip's. No on-disk representation that keeps deleted entries past compaction. State: mechanism present (4.10). No new functional test with `-prune`; no pruned sync measured in isolation.
- **C6, optional indexes unchanged.** `BlockConnected` fires per block in height order after the block's undo data is written; the indexes see exactly what they see today. State: shown for one case (`feature_async_undo` with `-txindex` and `-coinstatsindex`).
- **C7, blocks kept in memory are bounded.** The `-blockcache` budget bounds the parsed blocks in flight; nothing holds a block past acceptance outside that budget, the window's blocks included. State: partly; blocks held by receive tasks, the window and the bins lie outside it (7.6).
- **C8, no additional thread pools; asynchrony through effects.** One pool runs the apply tasks and the prevout fetch tasks; the script check queue remains for the tip. A block waiting for lower blocks holds no thread. All I/O stays on the effects executors, except two blocking reads issued by the apply workers: database reads for old coins, and the read of a window block's own block file when the block is neither passed in nor in the block cache (`RunConnectTask()`, with the release of old block files from the page cache that follows it). State: the block file read was added as an exception on 16 November (the maintainer, question 3 of the blind-spot assessment: moving it to the effects executor or to the connector would add a serial section; no code change); amended 15 November (the maintainer: the helper threads are fine, the short-lived flush threads not): the connect pool, the effects executor thread and the connector thread are accepted beside master's script check queue; a forced flush's further workers are tasks of the connect pool since commit 48 (claimed ranges, so a flush holding cs_main never waits for a queued task).
- **C9, optimise for mainnet.** Every measurement and bench uses mainnet data or mainnet blocks where one can be used. Empty blocks and signet are not design inputs. **C10, measure, don't guess; gains hardware-independent.** No knob is estimated. Expected gains are ratios derived from a measured share, never times on a machine class. Measurements on real data are the maintainer's to run. **C11, no time or effort estimates.** Sequencing and gates only. State of the three: process rules, kept.
- **C12, per-block fixed costs are multiplied by the block count.** Each stage states how many hand-offs per block it adds, keeps that number fixed and small, has a bench for it, and the tip path has none. State: counted 15 November from the code: a block from a peer in initial block download crosses threads about five times (handler to receive task, task to connector, connector to window task, worker's `applied` back to the connector, undo write to the effects thread with its BlockConnected riding the same queue), plus one for a continuation; a tip block three times (handler to connector, undo write and notification, the block freed by a pool task). The tip departs from "none": both tip hand-offs were measured at no cost (tip latency parity, the connector decision); the pool's wake-up has its bench (threadpool bench, with the pause as baseline).
- **C13, the flush is a symptom.** The cause is removed, the total order and the burst write-out, not the symptom. A change whose only effect is to make the flush less visible does not count toward a gate. State: amended 15 November (the maintainer): the cause is removed by the lag (runs of the oldest changes); the write path's own efficiency work (key-range shards, sorted whole-shard batches, the flush workers) is accepted on its own merits and counts toward no gate, since the full write still happens at shutdown, a cache resize and the periodic write.
- **C14, trust unchanged.** Nothing is assumed beyond assumevalid. Every consensus rule is evaluated; a deferred check is evaluated later, never skipped, and a check whose input is unknown fails rather than defaulting. State: holds.
- **C15, deliverable form.** An mbox of per-commit patches that applies to master with `git am --3way`; nothing is pushed; no code until the maintainer triggers it. The kernel library is not built during development; every new source file that belongs to it is added to `src/kernel/CMakeLists.txt` in the commit that introduces it. Commits carry no assistant trailers (the maintainer's later word, superseding the plan). State: holds; the kernel source list is complete, the kernel library never linked on this branch.
- **C16, existing tests are the oracle.** Functional tests are not changed except where an on-disk file or a log line they read has changed, each edit named in the commit message. Unit tests change only where the interface they call changed, minimally. New tests may be added freely. A design that would need an existing functional test rewritten is a finding against the design. State: six departures, accepted 15 November (the maintainer), each following from a deliberate behaviour change and none weakening its check beyond the documented notification order. Functional: `p2p_segwit` (one log text; `feature_coinstatsindex` is master's again since the forced write before a reorg went, 14 November). Unit: `chainstate_write_tests` (the subscriber reads the flushed block from the locator since the flush is asynchronous, the heaviest of the six), `validation_chainstatemanager_tests` (default and clamp value), small additions to three fuzz targets. `p2p_ibd_stalling` passes with the request rule.

Given by the maintainer after the plan, without a number:

- **The low-end write-out logic stays** (lag runs, eviction, the owed erase). Holds, with unit cases (`streamed_run_records_the_settled_head`, `evict_clean_and_bound_for_bytes`, `owed_erase_survives_a_create_and_its_unwind`).
- **Network work changes the receiving side only, no protocol change.** Holds: `net.cpp`, `net.h` and `protocol` untouched. A peer can observe two things: a ping is answered only after that peer's handed-off blocks are processed, and a slow peer is asked for fewer blocks at a time.
- **C17, performance work treats every block alike (15 November, the maintainer).** No code asks whether the chain is at the tip, or whether a block is the only one in flight, to choose a cheaper path; and a gain for connecting a single block applies to blocks connected during initial block download too. Decisions may follow from the data (how many of a block's inputs miss the tier), never from where the chain is. Rules out a solo-block confirm and an inline connect when the connector is idle; keeps an unwind driven by the block's undo data instead of a per-change record, and a prefetch sized by its misses. First step: a split timing of Confirm() and a warm-scripts tip bench.
- **No LevelDB tuning.** Holds. There is no LevelDB LOG file in the chainstate directory to ask for; the direction is the pipeline and our side of the flush.
- **Allocation failures terminate and logic errors stay uncaught.** Holds (4.5 for the pool; the broad handler around the compaction names `std::system_error`).

Never checked: the kernel library link; crash recovery under load; C3's benches; the historical chainstate under a snapshot, which gets neither window nor connector.

The four wordings once open here (C8, C13, C1's purity, C16) were ruled on 15 November (4.11). The list as yardstick was taken as accepted with "Continue".

## 3. Invariants

From the behaviour-only specification of 2026-11-09 (the specification and its 149 checks were used up by a review round and removed). Worded for that state and not re-checked against today's code; I6 names released entries, which went with the sweep (4.2).

- I1 Readers under the main lock see a chain tip and a UTXO set of the same height; a block's changes appear atomically with the tip update.
- I2 Every consensus verdict (accept or reject, and the reason), the undo data and the fee total equal in-order validation's.
- I3 Before a run the database holds the state at the marker's old head; each write is the outpoint's value at the new head; replay repairs any prefix. The settled head after a run is a block whose state the database holds.
- I4 A fresh entry is never in the database; an entry collected by a run is not fresh; a spent dirty entry is kept until its erase lands; a coin created and spent inside the lag is never written.
- I5 Change tags: the block height for connects; the fork height for a reorg's inverse changes, except restored coins created above the settled height; every change tagged at or below a run's bound is carried by the run, or holds the settled height down.
- I6 Unreleased entries are never evicted, never written as a block's unconfirmed change, and are released exactly when no open block refers to them.
- I7 Conflicts are charged to the block at fault, which fails at its confirmation; a block's own verdict is never altered by another block's actions on the view.
- I8 Every block above a failed or abandoned block is unwound before anything else happens; an unwound block's creates vanish and its spends are forgotten.
- I9 No pool task waits for a task of its own pool; the connector never waits on a worker that waits on the connector.
- I10 Block index batches commit in preparation order; the marker never names a head whose block, undo and index data are not durable.
- I11 The window never makes the node accept a block it would reject alone, or the reverse; outside IBD the behaviour is master's.
- I12 A crash at any point (inside a run, inside a block, at a reorg, at shutdown) is followed by a start-up replay that yields a UTXO set equal to that of a node that never crashed.
- I13 Memory: the tier's usage is bounded by `-dbcache` as the cache's was; the window holds at most its size in blocks and view maps.

### 4.2 The store: entries, records, visibility, locks

No entry is visited a second time when its block is decided (the sweep that did so was the largest worker phase, 36 to 42% of worker wall time, and was removed). An entry tells whose it is by height: `block_create` on an unspent coin at the coin's height, `block_spend` on a spent entry at the block's height, and the store's `m_confirmed_height`; `Pending()` is "flagged and above the confirmed height". A create is a dirty entry on the list of its height from the apply on (under an owed erase it keeps that change's height). A spend moves the coin into the block's record (`WindowBlock::record`, a vector under the slot mutex) and leaves a dirty spent marker, or erases a fresh entry (but see the spent mark, 4.6). `See(entry, viewer_height)` returns NOTHING, COIN or RECORD; a reader, or an applier below the spender, takes the coin from the record of the slot at the marker's height. `ConfirmBlock()` stores the confirmed height and drops the record; `UnwindBlock()` replays the record backwards.

Lock order: shard, then slot mutex; never two slot mutexes except the lower block of the two taking the higher one's; never slot mutex, then shard. `Record()` cannot leave the shard hold: an item has to be in the block's record before the shard is released, because `RecordCoin()` lookups, displacement in `SpendLocked()` and `CollectRecords()` rely on it. Seen and not changed: `ApplyBatch()` reserves the record to the exact new size on every call, so a continuation's second call reallocates the whole record under the slot mutex.

`GetDirtyCount()` is the shards' dirty total less the `dirty_delta` of the applied slots; `SanityCheck()` asserts it against the entries and the records. `CoinsStore::AccessCoin()` returns the calling thread's copy, good until the thread's next call, never a reference into a shard (an applier can move or erase the coin under the shard's lock alone, whatever lock the caller holds).

Shards. 256 (`CoinsStore::DEFAULT_SHARDS`, measured in 4.9), picked by key range (4.8). The shard mutex is a `ShardLock`: on a failed attempt it yields and retries for 20 microseconds before it blocks (the plain `Mutex` under `DEBUG_LOCKORDER`). `ApplyBatch` and `FetchFor` visit shards through `VisitShards` (outpoints sorted by shard, a first pass over the shards free at that moment, a blocking pass for the rest). Byte, entry and dirty totals are in per-thread stripes (`Totals`), so the publisher's size queries read no shard. Harness, 8 workers, when built: 468 blocks/s against 401, 1.17x; time asleep inside tasks 15% to 5%. Under a reindex the publisher is the thread `b-initload`.

Dirty lists per shard are a vector of spans indexed by `height >> 10`; entries keep their exact height and the bound is checked inside the span that holds it (unit case `bounds_are_exact_inside_and_across_dirty_spans`). The tree per shard keyed by height had cost a node per dirty coin; memory per output on the maintainer's run fell from 207 to 147 B.

Judged by reading, nothing measured:

- An entry reached over a list is erased by its key (one hash and bucket walk instead of two with libstdc++).
- The copy of a run's coins into its chunk stays: serialising straight from the entry would hold the shard through the serialisation. Scripts up to 36 bytes are inline, so the copy is about a hundred bytes and no allocation for every common output type.
- Scripts above the assumevalid point: a windowed block runs its scripts inline on its one worker, so with `-assumevalid=0` the whole chain runs on the window's threads where master uses `-par`. Never measured as a comparison (the one such run is in 7.1).
- The kernel library does not link `common/system.cpp`; the window reads `std::thread::hardware_concurrency()` itself.

### 4.3 Memory made on one thread and freed on another: kept-node lists, the depot, block bins

Kept-node lists. A map node freed by a thread goes on that thread's own list, up to a bound of 1024, and serves its next insertion into whatever shard; nothing is tied to a shard, the accounting per entry stays exact, and the unaccounted part is at most the bound times the node per thread (128 KiB). The alternative of a pool per shard (upstream's `PoolResource`) was dropped because it strands memory: a pool's free nodes serve only their own shard and the shards are uneven; the cache accounting does not see the stranded part, and accounting by chunks would break eviction (trial figures in 7.3).

The depot. A thread keeps the list it fills and one full list beside it; with both full it gives one to a static depot (64 lists of 1024 nodes, 8 MiB at most, never destroyed), with both empty it takes one. The depot's count is read without the lock first (taking the lock at every allocation with the depot empty raised the parks). Unit case `freed_nodes_serve_another_thread`. Why the kept list overran (likely, not counted): batches are lopsided, a continuation batch mostly spends, a connect-task batch mostly creates. Harness (chain D): 16 workers 502 to 528 blocks/s, parks per run 7,060 to 5,750, resident 440 to 447 MiB; 2 workers 82 to 88. The harness has a few hundred parks a second per worker against ten thousand on the maintainer's machine, so it shows no harm, not the gain (the gain is in 7.4). Talked through and not taken: a freeing thread, a preallocated region, another allocator.

Block bins. A block built on the connect pool is freed by the thread that built it (`BlockBins`, a bin per thread owned by the `ChainstateManager`, emptied before the thread builds its next block and drained by `ActivateBestChain()` once out of initial block download; a node that connects nothing further keeps at most a window of blocks until shutdown). With it, a window worker hashes the transactions of the block it reads itself. Tried beside them and dropped: notifying the connector only for the lowest block in flight (nothing measurable); one bin shared by all threads (0.8x, the thread is the point). Harness figures and lessons in 7.3.

### 4.4 The lagging database: marker, runs, eviction, the owed erase

Three correctness flaws of the first pass, fixed, each with a test:

1. The marker on disk was one run behind the written head in memory, while the lag ceiling and the prune gate decided by the value in memory; a pruned node at the ceiling could crash needing blocks already unlinked. Fix: a run's last write rewrites the marker to (new head, settled head).
2. A coin created and spent inside the lag is erased without a trace; if a reorg disconnects the spend and restores the coin, and the next multi-batch run stops after its first batch, the replay rolls forward along the new chain and the coin is lost. Master cannot do this, since it elides only coins created after the last flushed head. Fix: before the first disconnect of a reorg, when the written head is below the tip, write everything (the forced sync), so the replay rolls back along the old branch with undo data. Cost: one full write of the dirty tier per reorg under `cs_main`, visible in `feature_coinstatsindex.py`. A narrower fix (carry the restored coins in the batch that writes the marker) is the fallback if reorgs at the tip turn out slowed. Still open: whether `feature_dbcrash` could reach this flaw by chance (its replacement blocks re-mine the same transactions, which hides the loss in most orders).
3. `ApplySpend` reads the base with the shard unlocked; a lower block's spend applied, written and settled in between would let a higher block spend a coin that no longer exists. Fix: a settle counter per shard, compared across the unlocked read.

A final run that overlaps publication is wrong as such: it would declare the database consistent at a block while a coin its successor spent was never written. A run therefore blocks the publisher (`StartWriteOutRun`: nothing is confirmed into the tier meanwhile; in initial block download the connector waits with `cs_main` released), so starting runs earlier only moves the wait. Overlapping them was judged by reading: the simple rule (cap the settled height below any uncollected dirty entry changed during the run) would hold the written height almost still, since published blocks spend coins of every age.

Runs:

- The write-out target is taken from the total the trigger measures; an event that only evicted does not move the periodic timer.
- The target is one half of that total since 17 November (three quarters before, with no rationale on record). Measured on the maintainer's machine, a reindex to 400,000 at `-dbcache=1024`: against one half, three quarters 0.96x (one pair), a quarter 0.92x, a full write 0.87x; a full write writes 42% more changes than three quarters. The connector is stopped 23% of the span at one half and at three quarters alike. Figures in /work/parallel-validation/performance-suggestions.md.
- Dirty lists per shard and height, a clean list with a second chance, the collected mark, and the streamed run (no copy of the run, no second lookup). Invariant: at most one collected chunk outstanding per shard, and a collected entry is never erased before its chunk settles.
- A streamed chunk fills across shards to `-dbbatchsize` by an estimate of each change's batch bytes (45 plus the script for a coin, 38 for an erase), so a chunk is one batch, sorted like a flush batch (4.8). Basis: upstream's #31645 (batch sizes from 4 to 256 MiB measured; 32 MiB the default; flushing 5 to 30% faster by storage; nothing gained past 256 MiB); no measurement of my own. A chunk of one shard had never reached `-dbbatchsize`, so the simulated crash of `-dbcrashratio` never fired and `feature_dbcrash.py` failed on its own check that nodes had crashed: the crash hook needs a full batch. `-dbcrashratio` also fires after a non-final call's last batch when that batch is over half the batch size.
- A run collects the shards (`CollectChunk()`, which skips pending entries unless an erase is owed under them) and then the records of the applied slots (`CollectRecords(bound_height, final, ...)`): a confirmed dirty coin an open block spent is written from the record as the coin it still is, an owed erase as the erase. `BeginWriteOut()` scans the records before it concludes there is nothing to write. The final flush runs `CollectRecords(head, final)` and one more `WriteRun` after the flush workers and before the closing marker.
- An erase owed under an open block's create (the block re-creates an outpoint whose spend the database does not have yet) is written by a run as the confirmed value, which is the erase; nothing is held back under an open block.
- After a disconnect the written head is not an ancestor of the head; a run started in that state is forced final, and after a disconnect below the written head every run is final until one has begun (4.11, D2). A prune flush gets a head-only run that moves the written head past the last block that may be pruned.
- Accepted gaps of `CollectRecords()`: (a) a slot decided between its two passes leaves its item for the next run; no block is confirmed during a run in the window, so this needs a caller outside the window. (b) A displaced item whose entry was fresh and erased is skipped; only a failing chain gets there. (c) A coin collected and then spent by an open block before the settle is written twice.

Found while building: the existing unit test `processnewblock_signals_ordering` gives one block object to ten threads; with a block's own checks outside `cs_main` the memo flags in `CBlock` raced under ThreadSanitizer. The three flags are atomic now (`BlockCheckedFlag`).

### 4.5 The window

Retry rule. A worker reads the store while the blocks above it change it and does not look into records, so a valid block below an invalid one can fail in its place. A window block's failure is therefore no verdict: `PublishConnectTip()` sets `m_window_retry_serial`, the window drains, the block is unwound and then connected alone, which decides. A node error is not retried. Cost: an invalid block in the window is validated twice.

No further conditions on when the window opens are to be proposed (the maintainer, on removing a rule that opened it below the BIP34 height: "I don't like that we are introducing more exceptions."). The height clause itself later went for a different reason (4.6).

Undo. A block's undo data is settled on the block's worker once it is complete (`ConnectBlockResult::undo_size`, `SettleUndo`; after the continuation for a block that deferred); harness full reindex 1.24x when built.

Size. The width when `-connectwindow` is 0 is twice the connect workers (`ConnectWindow()`), at most `MAX_CONNECT_WINDOW` 64: the store's window table has a fixed `MAX_WINDOW_SLOTS = 128` that `SlotAt` and `ClaimSlot` scan linearly, so a wider window is a change to the store, not a constant. Above 32 threads the window is less than twice the pool; above 64 the further threads only take received blocks and the tip's prevout fetch. The byte cap is `max(coins cache / WINDOW_BYTES_SHARE (8), MIN_WINDOW_BYTES (32 MiB))`; the eighth is a choice, not a measurement, the floor is about six late mainnet blocks. `WindowBlockBytes()` is an estimate, (transactions + inputs) * 512 but at least the block's own size, plus the view's own usage, about 5.4 MB for a late block. The size floor (15 November, the first memory claim, option A on the maintainer's word) closes the understatement of a block of few inputs with large witnesses; the size comes from where it is known already, the block cache's measure at insertion (`BlockCache::Take()`'s `bytes`) or the length `ReadBlock()` read (`bytes_read`), so the worker reads no block memory for it. The window's cap reads the configured coins cache size, never its usage, so a full `-dbcache` does not narrow the window. The cap is the intended memory bound for small machines. On the harness at `-dbcache=450` it is 56 MiB and held about ten blocks in flight whatever the worker count (a false plateau past ten workers, from Benchcoin's setting); at the default of 1 GiB it is 128 MiB, about 23 of these blocks, and touches only windows of 24 and wider: reindex 164 / 294 / 416 / 492 blocks/s at 4 / 8 / 12 / 16 workers. With `-dbcache=4000` the window fills and a block takes longer from staging to publishable (53 to 64 ms against about 30) with more transactions deferred.

The continuation's fetch. `BlockApplyView::ApplyChanges` clears `cacheCoins` after the first pass, so in `RunContinuation` every input of a deferred transaction is fetched singly (`CheckTxInputs`, `AccessCoin`, `FetchCoin`, `ReadBase`, `CoinsStore::PeekCoinFor`): a shard lock per coin and on a miss a database Get. In core an input the batched fetch did not return is asked for again singly (`HaveCoin`), a shard lock and a database Get; with the BIP30 check off the database reads left equal the deferred transactions, one missing read each. A trial that keeps the first pass's coins is parked (7.4).

Exceptions on the pool, on the maintainer's word ("if it is not a std::runtime_error inherited exception, then just terminate"): `RunConnectTask`, `RunContinuation` and the hashing pool's `FinishChunk` are noexcept and catch std::runtime_error alone. Consequence: the store's logic_error "Attempted to overwrite an unspent coin" on a pool worker terminates the process where it asked the node to stop before. The std::logic_error handlers and the applied guard are gone. The defect as found is in 8.3.

Kept bench lines after the consolidation: `Worker phases wall/cpu` with five phases (read, fetch, core, batch, cont) and the connector's lines. The lock-wait accounting, the `Block life` line, the exact size count per window block and the record's free on the pool were removed (the record is destroyed where it goes out of scope, after the slot mutex is released).

### 4.6 BIP30 in the window, the spent mark, the stretch below BIP34

The gap, as found in 8.3: a window block's BIP30 check did not see a never-written coin that a higher open block had spent.

Closed with a spent mark, on "Ok, implement it." `CoinsStore::BeginBlock()` and `BlockApplyView::BeginBlock()` take `mark_fresh_spends`: an open block's spend of a never-written coin leaves the same spent marker as any other spend instead of erasing the entry. Every other path already understood the marker: `See()` sends a lower viewer to the record (its BIP30 check finds the coin, the block fails and is connected alone by the retry rule), `UnwindItem()` restores, `CollectRecords()` writes the coin from the record. In `CreateLocked()` a pending spent entry under a create returns the conflict before the "overwrite" throw. A block that creates and spends a coin itself leaves the marker too. Validation gives the flag, for a block of the window only, as `OpenBlocksCheckBIP30()`: BIP30 checked for the block or its ancestor `MAX_WINDOW_SLOTS` below. On mainnet the flag is on below BIP34, for the 128 heights above it, and from 1,983,702; on chains whose BIP34 hash never matches (regtest, signet, testnet4) always, so regtest connect figures across this change need the probe binary (6.3). Test `fresh_spend_marked_for_lower_create`. No test drives a duplicate outpoint through the real window end to end.

The marker of a never-written coin is dropped at write-out, not erased (`Entry::unwritten`, commit 30): as first built the mark cost 0.85 us a spend at the shutdown write (erases of keys the database never had). And it is freed when its block is confirmed, on "Ok, execute on it.": `ConfirmBlock()`, for a block that marked, walks the record it is about to free and erases the entry of each spend of a fresh coin if it is still that block's unwritten marker; the `CollectChunk()` and `WipeShard()` branches stay for a run that meets a marker in between. Before that fix the markers stayed in the map until a run or the flush (the 18:00.87 run, 7.1).

With the mark in place the height clause of the window rule was deleted (commit 40, on "Yes, then implement all four."), so the window opens from the start; the stretch below BIP34 had been about 72 s of a run on one thread, about 3% of the blocks.

The two overwrite blocks (91,842 over 91,812; 91,880 over 91,722), read in `CreateLocked()`, `UnwindItem()`, `CollectChunk()`, `CollectRecords()`: over a written coin the create goes over it and an unwind shows the database's coin again; over a confirmed unwritten coin the erase is owed and an unwind leaves the outpoint spent, as upstream's disconnect does; with the first block still open the create is a conflict and the block is connected alone, one window unwind each. An Assume on that path, reachable on the serial path of a build that aborts on Assume, was removed with a comment on the two blocks.

Measured on chain E (6.3) at 8 workers. Small blocks: serial about 950 blocks/s at any worker count, window 2920 / 5890 / 8980 / 7360 at 2 / 4 / 8 / 16 workers (3.1x to 9.4x; the fall from 8 to 16 is in 7.4). Empty blocks: 10500 serial, 17000 in the window (bound by the one publishing thread). With BIP34 at 100000 the stretch runs 8680 to 9250 blocks/s in the window against 930 to 1020 serial; the serial path is at 1190 to 1300 (1240 to 1340 before the mark); shutdown write 156 to 186 ms against 420 ms with the erasing mark. With the marker freed at confirmation: entries at the end 11,573 against 371,573, 8410 to 9860 blocks/s against 7730 to 8580, resident 156 against 199 MiB.

The confirm step split (a probe branch, chain D heavy section, nothing on the series). CPU a block in microseconds at 16 / 4 workers: marker walk 2685 / 3000, record free 217 / 307, everything else about 12. Per item: the record's free 20 to 28 ns, the walk about 0.5 us a marker (a table lookup that misses the cache, an erase, a cell free under the shard's lock). Above BIP34 mainnet marks nothing, so its Confirm is the record's free: 6.2 billion items at 20 ns is 124 s against the 130 s logged. Where blocks are marked (mainnet below 227,931, regtest always) the walk is ten times the free; on mainnet that stretch is 8.8 s of Confirm in all.

### 4.7 The receive side

Goal and rules. The maintainer paused the connect work at the 17:39 run ("17 minutes is good") and set the next subject, the network side of a sync: a local simulation; a generated regtest chain of full-size blocks; served by a bunch of nodes on unmodified master; only the receiving side may change; no signet. The goal: twice master's speed with heavy blocks, master as the client against the branch as the client on the same chain. Stated limit: where master already takes all the links deliver, no receive-side change can double it. A mainnet snapshot route was talked through and not taken (no clean way to fetch one here).

The receive pool. `PeerManagerImpl::HandOffBlock` decides from the 80 header bytes: in initial block download (never with `deterministic_rng`, so never in unit or fuzz tests), with the header's hash in `mapBlocksInFlight` for this peer, the message's bytes go to a task of `m_chainman.m_connect_pool`. Handler and task share `ProcessBlockMessage`: deserialise, mutation check, bookkeeping, the three-hold acceptance, the write, the block cache, the connector's signal, the same functions in the same order as master's handler. The task hashes the transactions itself and leaves the activation to the connector. `RunBlockTask` is `noexcept` and catches only `std::ios_base::failure`. Shutdown: `PeerManager::FinishBlockTasks()` after `connman->Stop()` and before `StopConnector()`. Test: `p2p_ibd_block_handoff.py`.

- Peer rules: a task sets the flag and wakes the handler; the handler checks `m_should_discourage` before the peer's next message and `SendMessages` disconnects first thing; a task drops its block when the peer is gone or marked, and the drop removes the request so the block is asked for again. So at most the pool's width of further blocks from a bad peer are processed, of at most 16 in transit. Bytes that are no block, on the pool, remove the request and disconnect the peer.
- The task limit is `WorkersCount() - 1` and is a correctness bound, not a tuning value. `Chainstate::DrainWindow` waits for the pool's window tasks with `cs_main` held, and a receive task takes `cs_main`, the only pool task that does; with every worker on a receive task both would wait for ever. A pool of one worker never hands off, which is why the functional suite (`prevoutfetchthreads=1`) sees every block on the handler. The handler waits for a free slot beyond the limit, so memory outside `-dbcache` is at most that many messages and their blocks.
- A block on the pool stays in flight until it is stored; without that the freed handler requested the same blocks again (4130 requests for 2449 blocks). But it does not keep one of the peer's sixteen places: it is flagged (`QueuedBlock::with_pool`) and `SendMessages` counts only the unflagged requests against the sixteen, so the pass that follows the block message asks for the next block. A peer can have sixteen blocks on the way plus the pool's task limit.
- A task always wakes the handler when done (at 24 workers 448 to 507 blocks/s against 371 to 405 without); the stalling timeout is cleared at the hand-off; a second copy of a block whose first is with its task is dropped; the task set is (peer, hash).
- Read and found sound: `NotifyHeaderTip` can deliver two header-tip notifications out of order (cosmetic, already possible against an RPC thread); `FlushStateToDisk(NONE)` in `FinishAcceptBlock` does work only on a pruned node, under `cs_main`, and waits for the effects executor; block-file order shifts by at most the task limit, pruning's bookkeeping is per file; `FinalizeNode` can run beside a task, which holds no connection.
- The hash pool is gone, since 15 November from the history too (how it left the history: the first-cut review record, 4.11); before that (commit 43): with blocks hashed in their tasks it served only blocks that stay on the handler and the block-file threads of a reindex, and neither it nor the block helper `DeserializeBlock()` showed outside the spread (7.7). `ProcessBlockMessage`, `ReadBlock` and `LoadExternalBlockFile` deserialise with the plain operator over a `SpanReader`, which hashes from the bytes; the loader reads a block's bytes into a buffer first for that. Were the loader ever the bound of a full reindex, its serial rate without the pool is about 0.83x (loader CPU 33 s against 27.5 s). The commit cancels most of commit 13; dropping both in a rewrite of the history is the maintainer's call. Alternatives weighed in the plan and not taken: transactions built on hash threads (strictly immediate disconnect, moves only deserialisation), one lane per peer (nothing for one peer), several message handler threads (outside this branch).

`-test=bip30_off` sets `Consensus::Params::bip30_off`, read by `ConnectBlockChecksBIP30()`, and BIP34 keeps regtest's height 1, so a full `-reindex` accepts the genesis block again (a first form set `BIP34Height = 0`; the genesis block then failed BIP34 on its version and its coinbase, and with no valid block `InvalidChainFound()` aborted on `assert(tip)`). `feature_connect_window.py` reindexes the blocks after the chainstate in both variants.

The kernel's block cache stays a fixed 128 MiB (`DEFAULT_BLOCK_CACHE_BYTES`), not clamped to the coins cache as bitcoind's is, and the C API cannot set it; documented at `ChainstateManagerOpts::block_cache_bytes` and at `btck_chainstate_manager_options_set_database_cache_bytes`. The `-par` help says the window's scripts are not bounded by it.

A requested block that does not deserialise: on the connect pool the request is dropped for the block to be asked for again and the peer is disconnected (noban and manual kept), so that it is not asked again to answer the same way; on the message handler master's handling stays, the exception logged and the peer kept until the download timeout. Making them agree would change master's policy for every block message; the reason is in the comment at `RunBlockTask`.

The request rule's test, `p2p_ibd_request_rule.py`, drives a peer's delivery times with mocktime, which both clocks of the rule follow (`NodeClock::now()` at receive, the request time in `SendMessages`): one block until the first arrived, one at a time at four seconds a block, then 1, 1, 2, 3, 5, 16 as it delivers at once, and back to one after a round at four seconds a block. It fails on master (16 asked for at once). Known limit, accepted: with one block outstanding the sample is the round trip, so a peer whose round trip exceeds two seconds stays at one. Also known: the rule limits how many blocks a slow peer holds, not which, so it can still hold the lowest missing block.

Blocks at the tip go to the connector too: `ProcessBlock` activates asynchronously whenever `deterministic_rng` is off, and `SignalConnector(block)` leaves the block just accepted for the connector's next `ActivateBestChain()` as the block in hand, so it is connected from memory and not read back. Test `p2p_tip_connector.py` (the tip's `UpdateTip` on the `connect` thread and a "Using cached block" line; fails when the connector is given no block). Measured with a throwaway harness (`tipbench/tip_latency.py`: a block of 2000 unseen transactions from one test peer, getheaders timed in a loop from another), four rounds each: the longest answer 110 to 117 ms before, 104 to 108 ms after, the tip in 143 to 151 ms either way; an older master binary (4519933391) 110.6 ms with the same 99 ms "Verify 2000 txins". So no cost and no gain: the handler takes the next message, but getheaders, getdata and nearly every other message need `cs_main`, which the connection holds through script verification as on master. A gain at the tip needs the scripts checked before `cs_main` is taken; not attempted.

The per-peer request rule (31 lines in `net_processing.cpp`). In initial block download a peer has outstanding at most one block more than it delivers in two seconds, going by a smoothed time between its block arrivals (weight 1/4; the sample is taken whenever `now >= since`, with a floor of one microsecond), never more than sixteen, and one until its first block arrived. Outside initial block download nothing changes. No message changes; a peer sees fewer hashes in a getdata.

### 4.8 The flush

Why master's shape stalls. The coins database's write buffer is 2 MiB (8 MiB cache / 4, `dbwrapper.cpp`), so every 32 MiB batch is its own memtable and level-0 file; 12 level-0 files stop writes (`kL0_StopWritesTrigger`) until the one background thread has compacted them. With shards picked by salted hash every file spanned the whole key space and each compaction rewrote level 1: one batch in 12.2 stalled. Also `WriteRun` put the marker keys (`DB_BEST_BLOCK` B and `DB_HEAD_BLOCKS` H, which bracket the coin keys C) into every batch, so every batch spanned all coin keys.

What is built:

1. `CCoinsViewDB` remembers the marker it left open (`m_open_marker` under `m_marker_mutex`): the marker is opened once in the first batch and closed by the final one; a `WriteRun` naming the same pair of heads writes coins only; `BatchWrite` and a final run forget it.
2. `ShardIndex` is `(ReadBE32(txid) * shards) >> 32`, the leading four bytes of the txid as the key serialises it, monotonic for any shard count; the in-shard map keeps its salted hash. Side effects: a transaction's outputs share a shard, and the shard pick is grindable (contention on one shard, not complexity).
3. A store batch is whole neighbouring shards and ends between two shards only, at most 32 of them (`MAX_BATCH_SHARDS`, 9.2); a shard larger than a batch is a run of its own, which `CCoinsViewDB::WriteRun()` cuts at `-dbbatchsize` along the keys. `-dbbatchsize` stays the bound on what the database is given at once; what grows is what a worker holds before it writes, a whole shard's changes (a 256th of the tier), moved out of the map, not a second copy. Each shard's changes are sorted into descending key order (`SortWrites`), walked from the highest shard down, because H sorts above the coins. `SortWrites` orders the outputs of one transaction by the outpoint, which is the key order except past the 16511th output (the key's VARINT of the index grows from two bytes to three and sorts lower bytewise); an overlap there is two pieces touching in one transaction, placed a level higher instead of merged.
4. `MAX_WIPE_WORKERS{4}`: a worker for every two batches of dirty set, capped by cores and shards, each with a contiguous range of shards; the one with the highest range runs on the calling thread, writes the marker's batch, and starts the others once it is in the database. A default cache of 450 MiB flushes on one thread; never more workers than cores.
5. The forced flush waits for the executor once more after `SettleWriteOut()`, since a completion applied there can queue the final sync of a completed undo file.

Why it works: LevelDB places a non-overlapping memtable down to level 2 (`PickLevelForMemTableOutput`) and moves files without rewriting (`IsTrivialMove`); read, not run. A cut in the middle of a shard's walk had defeated it for a shard of more than half a batch (any flush above about 4 GiB at 256 shards): the walk is in the map's hash order and each piece was sorted after the cut, so the two pieces were two batches over the same key range, batches overlapped in a chain down the shards, and the database fell behind and stopped its writers. Hence item 3, not more shards: the maintainer's objection ("Doesn't more shards = more baseline memory, which is not compatible with the low-power setups restriction?") stands unanswered by measurement (only the harness's level peak resident memory from 16 to 4096 shards on a short chain; the per-shard footprint on a long chain, the dirty spans in particular, was never read or measured), and the stalls were a large-cache condition, so raising the default would charge every setup for it.

Upstream: #31875 sorted batches (a 26 GiB dump from 21:56 to 8:27), closed by its author when later benchmarks cast doubt; sipa's objection was the sort's memory at the peak, which sorting a shard at a time does not have.

Unit cases: `flush_batches_are_disjoint_key_ranges`, `flush_never_ends_a_batch_inside_a_shard`; `flush_fills_batches_across_shards` changed minimally (it had counted on the fill inside a shard). Not exercised: a crash in the middle of a flush or between lag runs under the remembered marker; a flush interrupted between the batches of four workers. Runs and probes in 7.1 and 7.2.

### 4.10 Pruning

Block files: `BlockManager::PinBlockFile()`/`UnpinBlockFile()`, both prune finders skip a file with a write in flight; the prune order of 4.11 (D1, D3).

The prune rule (commit 41). Pruning never passes the coins database's written head, and nothing else limits a pruning node's lag: the fixed ceiling (`LagCeiling()`, 256 in prune mode, a run about every 129 blocks at any cache size) is removed.

- The limit. `FlushStateToDisk` caps the height both finders may prune to at the written head; when the written head is not on the active chain the cap is the fork point with the active chain, so the left branch's blocks above the fork stay too. A file is unlinked only once a block index that records it is on disk (D1 of 4.11), and that index is written after the coins the limit was computed from are on disk, so at no instant does the durable index call a block pruned that a replay from the durable coins database needs.
- Bringing the database forward. When pruning would take files, a write-out run to the prune height is started before the finders choose, and settled before they run. Two conditions gate it. Pruning would take files: a manual request is pending, or `BlockManager::AtPruneTarget()` holds, which repeats the conditions of `FindFilesToPrune()` (the chain above `PruneAfterHeight`, the block files plus one chunk of each kind at the target). And the written head holds a whole file back: `BlockManager::HasBlockFileEndingWithin()` finds a block file ending between the written head and the prune height. The first form, a run at every prune check, fell from 120 to 43 blocks/s; the second, the file condition alone, made a run for each block file from the start of a sync, also while the files were far below the target and nothing could be pruned (found by the review of 4.11 and by the reimplementation, whose gate counts the held-back bytes against the target; the predicate here is the coarser form of the same rule). A node that prunes only on request writes nothing without one. The disk space is checked before the run as before a flush (`CheckDiskSpace`, "Disk space is too low!"), taken from the reimplementation. A run is refused with an error once a flush or a run failed (`FlushFailed()`), where it had reached an `Assert`.
- What it bought (H, 7.7): a pruned sync at `-dbcache=450` at the same rate (121.1 against 120.4 blocks/s) with 0.55x the coins written and 2,269 erases against 232,428; 23 database commits where the ceiling had asked for a flush 1016 times. At `-dbcache=30` the cache drives the runs and nothing changes (37.2 against 38.1).
- The two gaps the ceiling had hidden, both closed: the run's effect committed the block index, with the chosen files already flagged as pruned, before it streamed the coins, so a crash inside the stream left a written head below blocks the index called gone (master has the same window between its index write and its coins flush); and the gate compared heights, not branches, so after a reorganisation deeper than 32 blocks a file holding blocks of the left branch could go while a replay still needed their undo data.
- The benchcoin cost that led here (7.5): `StreamWriteOut` 330 to 395 s of CPU, the database's background thread 1340 s where near-master's has 279 s, 390 GB written for 102 GB received, all with the ceiling. No real-network run without it exists.
- Test: `feature_coins_lag_prune.py`, a crash inside the coins write of a manual prune (the existing `-dbcrashratio=1 -dbbatchsize=300`), then a kill right after files were deleted; each restart rolls forward to the same tip and UTXO hash as an unpruned peer. Never exercised by any test: automatic pruning together with the lag, a written head off the active chain, a crash between the index write and the unlink, a snapshot chainstate.

### 4.12 Built and taken off again: the spend hints and the young table

Neither is on the series (tip then 74e8e1db9a, 22 commits). Both were built on 2026-11-18 as commits on top, and both are kept on branches of their own.

**Window matching** (branch `utxo-partial-order-matching-trial`, two commits on 343b027776: 0b53f504d7 and e8c9e32e81; built 2026-11-19 on the maintainer's go after an outside suggestion to match spends inside the window before validating). A lower window block announces its transactions with a source; a higher block's read of an input that lower block has yet to apply takes the coin from the transaction (position kept beside the id in the pending table, checked by the id), checks and applies the transaction in its first pass, and holds back only the spend of the matched coin, which goes with the continuation's apply once every lower block is applied. The spend carries the coin it was checked against (`known_coin`): a coin spent before it or another coin is a store conflict, and the block is connected again alone. `-test=no_window_match` restores the deferral in the same binary. Gates: unit suite 397/397, the window functional tests (matching exercised, 5 to 11 matched spends a run, a crafted invalid block retried alone as before). Harness, `-reindex-chainstate` of chain DX, `-dbcache=1024`, five alternating rounds: deferred transactions 671,000 to 27,000, 713,000 matched spends, no conflict; first form 312.3 against 320.8 blocks/s at 8 cores and 481.6 against 505.5 at 14; after the position table and the merged apply 309.2 against 319.6 (8 cores, -3.3%) and 489.3 against 500.2 (14 cores, -2.2%, ranges overlapping), CPU per run within about half a second. Why it does not pay here (a throwaway probe of the workers' phase CPU): finishing all deferred transactions cost only 1.9 s of about 48 s, since the deferral already skips the wasted lookup (commit 16) and continuations run in parallel; matching moves that work into the first pass and adds a little to the applies. On the maintainer's machine (19 November, -reindex-chainstate to 975,073, -dbcache=30000): 12:08.21 and 17,838 s user against 11:57.62 and 17,354 s on the series tip, with 79,348,729 transactions still deferred (375,315,841 without matching) and 429,680,922 matched spends, 1 conflict, 1 block retried alone: 1.5% slower, 2.8% more CPU. The remaining deferrals are probably inputs whose place in the fixed table of announced ids (2^19 places, a 64-block window) a later id took; not measured. Matching does not pay on mainnet either. Not on the series. `-test=no_window_match` is refused outside regtest; a debug option `-windowmatch` was begun on the branch, uncommitted, and stopped on the maintainer's word.

**The spend hints** (branch `utxo-partial-order-spend-hints`, commits 6c73dd423e and b1d6cc0fd5). The maintainer's assessment of 2026-11-18: fairly useful for IBD; no figure is recorded, and they stay off the series until asked for. They are for a sync whose cache is smaller than the coin set. Without them a write-out run made to free memory writes coins that a block already received is about to spend, and each such coin costs a write and, a few blocks on, an erase: on chain M at `-dbcache=30`, 3.9 of 8.8 million written coins are erased again later.

- The note. `ProcessBlockMessage` notes the inputs of a requested block whose parent is known in `ChainstateManager::m_spend_hints` (`SpendHints`): a direct-mapped table of 2^20 atomic words, 8 MiB, allocated by the first run for memory and not counted as cache. An entry is void once the chain is at the spender's height; the horizon is 1024 blocks. Until the first run for memory a note is one atomic load.
- The run. A run started for memory pressure, and not waited for by pruning, passes `CoinsStore::Hold` with an allowance of half the bytes it was to free. It leaves a confirmed coin that is fresh, created above the height the database held before the run and within `HOLD_DEPTH` (144) of the run's head, if a note names it or an open block spent it. The coin stays dirty, so it is not evicted and counts in the budget. Periodic, final, forced and prune runs persist everything as before, and no window rule changed.
- Crash safety. The run settles one block below the oldest coin it left, so the existing replay covers a crash. Because a holding run settles below changes it wrote, a disconnect below the highest bound written forces a final run (`m_written_through`), and so does a coin restored during a holding run in the range where the settled height is not known yet (`TagFor`).
- Where they act. Only where blocks arrive from peers and the cache is under pressure. A node whose cache holds the whole set never makes a run for memory, and `-reindex-chainstate` receives no block from a peer, so neither shows them (the full-memory reindex run of 7.10 is the same with and without).
- Measured 19 November, ported onto the series tip (branch `utxo-partial-order-spend-hints-trial`, 8e7bf94f87 and ded5544e01 on 343b027776, cherry-picked without conflict; unit suite 397/397, the pruning and window functional tests pass). Harness SYNCS of chain DX (three master peers, client on 8 cores), three alternating rounds against the tip, `cpu/hints_ab.sh`, log `cpu/hints-ab-2026-11-19.log`. At `-dbcache=30 -maxmempool=5`: 45.4 against 41.2 blocks/s (medians; 44.0 / 46.0 / 45.4 against 41.2 / 41.1 / 41.7, every hints round faster than every tip round), client CPU 177 to 181 against 195 to 198 s, coin changes written in runs 13.3 against 16.85 million (-21%), 1,517 against 1,937 MiB, erases 6.57 against 8.34 million, peak RSS 434 to 441 against 476 to 495 MiB. At `-dbcache=450`: 231.4 against 236.6, no write-out run in either (chain DX's coin set fits the cache), so the hints have nothing to act on; a test there needs a chain whose coin set exceeds the cache, or a real sync. A 10% gain at the harness floor, with fewer writes and less memory; whether it carries to 450 and mainnet is open. Local mainnet syncs the same day (`ibd/local_hints.sh`, log `ibd/local-hints-2026-11-19.log`): a plain master serving node with mainnet to height 250,000 (11 GB of blocks, downloaded once; `-whitelist=download@127.0.0.1`, no outbound connections), the client on 8 cores from a fresh datadir with `-dbcache=100 -maxmempool=5 -minimumchainwork=0 -assumevalid=<block 250,000>`, three alternating rounds: wall 2:35.50 / 2:27.71 / 2:27.75 for the tip against 2:29.14 / 2:30.79 / 2:30.68 for the hints, 854.7 blocks/s over heights 150,000 to 250,000 for both (one hints run 847.5), 45 write-out runs and 14.02 million coin changes written in every run of both. The hints held nothing ("0.0 MiB left for blocks received to spend" in every run): each run's bound was 3,800 to 9,600 blocks below the head when it started, so every coin it wrote was far older than the 144 blocks (`HOLD_DEPTH`) a held coin may be, the bound that keeps the written head, and with it a crash's replay, close behind. On chain DX at 30 MiB the cache holds only a few dozen heavy blocks of changes, so the coins a run writes are young. What decides is how many blocks of changes the cache holds: with today's blocks (thousands of coin changes each) a 1 to 4 GB cache holds on the order of a thousand blocks or more, so the hints as built would rarely act at typical sizes, and help only caches holding under about 144 blocks of changes (an estimate from the mechanism, not measured). A deeper `HOLD_DEPTH` would reach further only by letting the written head fall further behind (longer replays), a change to crash recovery. Dropped on the maintainer's word (19 November, "lets revert this change again"): they help only caches holding under about 144 blocks of changes, and a deeper limit would cost crash replay length, more reorgs forcing a full write and more memory pressure for an unmeasured gain. They were never on the series; both branches stay as a record (`utxo-partial-order-spend-hints`, `utxo-partial-order-spend-hints-trial`).

**The young table** (branch `utxo-partial-order-young-table-trial`, commits 08c05b4dca and 7abcf2575f). A small table for each shard, beside its main one, for the coins blocks create: option 2 of the maintainer's grouped-commit notes. Measured slower by the maintainer (7.10) and dropped (8.1).

- The table. Inside each shard's map, under the shard mutex: an array probed in line with twice as many slots as the entry limit, each slot the hash beside the cell, so a probe for another key reads no cell. It is made with the first entry and freed by a flush. The slot of a hash is its product with a constant, because the hashes of one transaction's outputs follow each other and would form one run. The cells are those of the main table and never move.
- The path. A block's create that is neither BIP30-checked (`must_be_new`) nor an overwrite is made there without a probe of the main table, as master's `AddCoin(possible_overwrite=false)` takes a create for fresh without reading the database. Every lookup probes the young table first. A full table is moved on to the buckets, which are asked for a stretch of 32 slots ahead; a flush moves it as well. A coin spent before that never touched the main table: not at its creation, not at the spender's lookup, not at its erase.
- The guard. The main table can hold an outpoint that such a create makes only as the spent marker of a disconnected block's output. From the first marker a change without a block identity leaves until a `Flush()` has emptied the store, creates go to the main table as before.
- The limitation. A txid made twice at a height where BIP30 is not checked (excluded by BIP34) would leave two entries for one outpoint; `SanityCheck()` asserts there is none, nothing else looks.
- The switch and the counters. Debug-only `-coinsyoungtable=<n>` entries a shard, default 0 for no table. At 1024 the 256 shards hold about 262 thousand entries in about 8 MiB of slots, at 4096 four times that. Every coins flush logs the totals since the start: made, ended there (never in a main table), moved on, lookups answered there against lookups that went on. On regtest the table fills only with `-test=bip30_off`.

**The compact entry** (on the series since 2026-11-19 as commits 26 baf4dc1de2 and 27 890928840b, on the maintainer's word, messages without the trial note and the figures; built on branch `utxo-partial-order-compact-trial` on 343b027776; the `-dbcache` clamp for the 256 GiB node limit left out by the maintainer; started 2026-11-19 on the maintainer's go, measured on chain DX only, by the maintainer's word). Aim: fewer bytes per coin, so that a cache sized from the machine's memory (RAM less the node's overhead, the chainstate's size on disk for the page cache and a margin, floor 1 GiB, cap the whole set; discussed the same day, not built) holds more of the set. The layout before: about 125 to 130 bytes an entry without a script's heap memory (chain link 8, outpoint 36 padded, Coin 48, write-out height 4, flags 2 padded, list links 16, bucket about 8), plus 48 to 64 for a script over CScript's 28 inline bytes. - Step 1, commit 30df57394a: `StoredCoin`, 48 bytes like a Coin, the script inline up to 35 bytes (every standard script, P2WSH and P2TR included), longer ones on the heap with their length; bytes unchanged, lookups hand out a Coin. Round-trip unit test `stored_coin_round_trip`; unit suite and the store and window functional subset pass. On chain DX (`cpu/compact_ab.sh`, log in the job tmp `cpu/compact_ab.log`, 8 cores): 137.4 against 145.5 bytes per coin at height 4,281 (-5.6%; chain DX's coins mostly have short scripts, so mainnet's taproot share would save more, not measurable here); -reindex-chainstate at 1024 319.6 against 321.3 blocks/s (medians of three); sync from three peers at 1024 233.8 to 237.2 against 234.7 to 240.2; at -dbcache=30 -maxmempool=5 42.1 / 42.4 / 42.5 against 41.7 / 42.4 / 41.3 blocks/s, write-out runs 147 / 144 / 148 against 157 / 157 / 156 (about 6% fewer). Neutral in speed, smaller in memory.
- Step 2, commit 5cc5657f49: 32-bit cell numbers for the chain link, the bucket array and the list links (region number high, slot low; node regions aligned to their 32 MiB size with their number in the first slot; a constant-initialized table of 2^13 region addresses, 64 KiB of static memory supplied page by page, 4 KiB per 16 GiB of nodes; abort past 256 GiB of nodes). StoredCoin keeps its amount as bytes so the cell packs to 104 bytes (120 before), bucket 4 bytes (8). Test `node_numbers_span_regions` (700,000 entries, about 73 MiB, three regions or more). On chain DX (`cpu/compact_ab2.sh`, log `cpu/compact_ab2.log` in the job tmp): 112.9 against 145.5 bytes per coin (-22%). With the region table first behind a function-local static, -reindex-chainstate at 1024 was 4.3% slower (315.0 against 329.3) and syncs at 1024 3 to 8% slower; with the constant-initialized table (folded in) 320.3 against 324.2 (step 1 318.4) and syncs 236.8 / 237.0 / 229.8 against 240.9 / 235.1 / 232.6: equal within the noise. At -dbcache=30 -maxmempool=5 (measured before the table fix): 43.5 / 44.2 / 43.3 against 42.8 / 41.7 / 42.5 blocks/s, write-out runs 121 against 155 (-22%), client CPU 178 against 192 s (-7%).
- Step 3 (heights and flags in one word) not built: after step 2 the entry has 2 bytes of padding and the allocator's cells are multiples of 8, so it saves nothing; without step 2 it saves nothing either (the pointers keep the entry at 72 bytes).

### 4.13 Sketch, not built: a large block validated in chunks (20 November)

Asked by the maintainer after the steady-state breakdown (5.2a: a heavy tip block with a full mempool spends about 8.4 ms in the serial core and 25 ms in the connect as a whole). The idea: split a large block's transactions into chunks and validate them as neighbouring entries of the window, so that the core's serial loop is spread over the connect pool. A design sketch only; nothing is built.

What is unavoidable, in any design: transactions spending outputs of earlier transactions in the same block (about a third of outputs are spent in their own block, 7.6); the per-block rules (fees against the coinbase, the sigop limit, undo data in transaction order). Not a problem: a double spend inside a block makes it invalid whichever spend comes first, so detection is enough, with the exact verdict from a serial re-run, as the window's conflicts already work. What is the series' own: the block as the unit of identity (window slot, change record, conflict order by height, AnnounceCreates per block) and a block-shaped core. Ruben's out-of-order design (7.6) has the transaction as its unit and would fit better, but needs a set that keeps spent outputs (against C4) and adds outputs on arrival, which the matching trial (4.12) found no faster here. The sketch therefore extends the series instead.

- Unit. A window entry is a chunk: a block's transactions [begin, end), the coinbase in the first. A block is split when it has more than a threshold of transactions (a property of the data, so C17 holds: a large block in initial block download is split as at the tip), into about as many chunks as the connect pool has workers, at transaction boundaries, each chunk about equal in inputs.
- Identity and order. The store's order key becomes (height, chunk) where it is height now: window slots, change records, the conflict rule (the lower key stands), the creates announced by an entry (AnnounceCreates, CreatesPendingBelow). A block's chunks are confirmed together, by its last chunk's publication; nothing outside the window sees a part of a block.
- Dependencies inside the block. A chunk's input made by a transaction of a lower chunk of the same block is deferred, exactly as an input made by a lower block is now (the lower chunk announced its txids), and finished by the continuation once that chunk is applied. A spend of an output made earlier in the same chunk stays inside the chunk's view, as now.
- The core. ConnectBlock takes a range of the block's transactions and returns the range's partial results: fees, sigop cost, input count, undo entries for its transactions, its deferred transactions. The per-transaction checks are unchanged (amounts, sequence locks, BIP30 per output, scripts inline on the worker as for any window block). The checks of a total move to the block's publication: the sum of the chunks' fees in money range, the sum of their sigop costs against MAX_BLOCK_SIGOPS_COST, the coinbase amount against fees plus subsidy (the core already defers this check when a block has deferred transactions: coinbase_check_deferred).
- Undo data. Each chunk's undo entries are its transactions' slots; the publication of the last chunk concatenates them in transaction order into the block's CBlockUndo before its write is queued (the core already leaves empty slots for deferred transactions and fills them in the continuation).
- Failure. Any chunk that fails, or a conflict between chunks, sends the whole block back to be connected alone (unsplit), which decides, as a window block's failure does now. A block that is invalid fails there with master's verdict and state.
- Signals and the block index. One BlockConnected, one undo write, one UpdateTip per block, at the last chunk; the chunks are invisible outside the connector and the store.

Work, in order: the (height, chunk) key through the store and the window; the range form of ConnectBlock with open totals; the publication's totals and undo assembly; the split rule; tests that a split and an unsplit block give the same state, undo data and verdict (valid, a double spend across chunks, a sigop total over the limit only in sum, a coinbase over fees only in sum).

Expected effect (estimates from the measured shares, not measured):
- Steady state (full mempool, scripts cached): the serial core of a heavy block, 8.4 ms, over about 8 chunks becomes roughly 2 to 3 ms (a fixed cost per extra entry of about 0.3 ms from the empty-block measurement, and a serial tail for transactions spending same-block outputs across chunks, finished by continuations). About 5 ms of about 50 ms receipt to tip: around 10%. The other 40-odd ms (mempool cleanup about 11 ms, the about 25 ms before the connect) are untouched.
- A whole block with cold inputs and scripts to run: the core, 44 ms on a heavy block, holds the coin reads and the input checks serially while the check queue runs the scripts; chunks would run both on 8 workers. Perhaps 20 to 30 ms of about 115 ms, 20 to 25%, the largest gain; depends on the serial tail.
- Initial block download: no gain expected and a small loss possible. The window already keeps the workers busy with whole blocks; chunks add entries, announcements and continuations for every large block. A gain only where the window cannot fill (a single large block holding up the connector, or a window narrowed by its byte limit), which the measurements found rare. A rule that split only when workers are idle would avoid the loss but asks the pool's state, near the edge of C17; to be decided.
- Small blocks (under the threshold): unchanged.

### 5.2a Tip connect performance

The maintainer's question: why is the tip no faster than master when initial block download is, given the allocator, depot, table and huge-page work? My answer, from memory and not checked against the code: (1) the tip latency harness (about 145 ms against 141.5 on an older master, verification about 99 ms on both) had largely uncached scripts, which run on master's own check queue; (2) the allocator, depot, per-shard tables and huge pages recovered costs the store itself brought (cross-thread frees, contention, misses in a large table), which matter with many workers in initial block download, not for one block on one thread against a warm cache, where master's CCoinsViewCache never had them; (3) the store adds per-block work at the tip: the tip bench (commit 47) has prefetch and core within a few percent of master's shape, Confirm() about 1.8x master's flush (about 1 ms on block 413567), the round trip 1.14x; the hand-offs (connector, effects) measured at no cost. Correction made in the discussion: a real tip block is rebuilt from the mempool and hits the script cache (WarmScripts is only about 1.5x NoScripts), so the UTXO side is a large share of a realistic tip connect, and the series may sit slightly behind master there.

Levers discussed, under C17 (no tip or solo-block introspection; a single-block gain applies in initial block download too, section 2):
- An unwind driven by the block's undo data and its own outputs, guarded per entry by the block's identity, instead of a per-change record built on the apply path; previous flags restored conservatively (dirty, not fresh), an occasional redundant write, as with the owed erase. Moves cost from every block to the rare failing one; helps the window as much as the tip.
- A prefetch sized by its misses: one pass taking each shard's lock once copies the inputs the tier holds (as BlockApplyView::Prefetch()); only the misses go to parallel database fetches, and only when there are enough to pay for the pool's wake-up. Decided by the data, the same for every block.
- Ruled out by C17: a solo-block confirm, and connecting inline when the connector is idle.

First steps when taken up: a split timing of Confirm() (record building, per-shard locking and tagging, the confirm itself) and a warm-scripts variant of the tip bench through the store and through master's overlay, to size what the levers can buy. Nothing started; waits for the maintainer.

### 5.7 Regressions, known and expected

The list for pass 3 at 82a1b90f76. The heavy-block sync and reindex rates show none (4.9, 7.7). The benches were not rerun after the fold of 4.11, so the two items the fold brought are unmeasured.

Measured, against master (figures in 4.9):

- Empty blocks at two cores: 0.78x to 0.96x of master's rate; ahead of master from four cores. The branch spends about 1.4x master's CPU on an empty block's own path and spreads it over threads that two cores cannot all run; the code that holds the extra cost is not identified (4.9).
- Resident memory: higher at harness scale at two and at sixteen cores; the window's blocks and the block cache are outside `-dbcache`.
- CPU on a sync from one peer: idle connect workers cost CPU, the same rate for 0.75x the CPU with two workers and a window of four. Cause not read.

Expected from the code, never measured:

- (Gone on 14 November: the forced coins write before a reorganisation; see the third review's fixes.)
- Outside initial block download `PublishConnectTip()` waits for the effects executor and applies its completions (the fold, 4.11), so the undo write is on the connect path again at the tip. Master writes undo on that path too: parity with master expected, a loss against the series before the fold possible.
- A PING is answered once the peer's own block tasks are done and the connector has attempted every activation signalled before the ping (the pending pong, accepted below): a delay of that peer's messages during a sync, documented and kept.
- The prune gate after the fold (4.10): the figures of the prune rule were measured with a run for each block file; the gate now makes no run below the prune target. Equal or better expected, not rerun.

Accepted, each with its lever if it is taken up (decided 15 November on the first cut; the current cut carries the same design):

- The node depot keeps its peak (the maintainer: "maybe we just need to accept this for now"): freed nodes stay in the depot for reuse, so resident memory stays at the initial block download peak, at most about `-maxmempool` above the budget once the mempool takes back its allowance. The lever: when the store shrinks below that peak, evict clean entries by region (the emptiest 32 MiB regions first, occupancy read from the depot and the threads' lists) and release a region once no live node is left, skipping regions with nodes in a thread's own list; no node moves. Compaction and a full flush-and-drop at the end of initial block download were weighed and set aside. Not measurable with -reindex-chainstate runs, which never leave initial block download.
- Freed blocks in idle per-thread bins ("accept that one for now"): a thread that builds no further block keeps what came back to its bin; after initial block download every `ActivateBestChain()` empties all bins, so only a node that connects nothing afterwards (an offline node after a reindex) holds up to a window of blocks until shutdown.
- The pending pong, documented and kept (no test-only machinery to preserve master's send-and-ping meaning). In the current cut a ping's answer waits in `Peer::m_pending_pong` until the peer's own block tasks are done and every hand-off to the connector made before it is done (`ChainstateManager::HandOffsDone()`), and no further message of that peer is taken meanwhile (`net_processing.cpp`); master's pong waits only behind that peer's own earlier blocks. Far inside the 20-minute ping timeout; the throughput lost in initial block download is not measured. Candidate fixes: an immediate pong in production with the hold behind a regtest `-test=` option the functional framework sets, or the peer's messages kept flowing with only its pong waiting.
- C5's replay cost (C5 amended, option A): a replay after a crash reads only kept blocks because pruning is held at the written head's fork with the chain, with a write-out run first where that holds a file back; the pruned node's lag cap is gone for good. Cost: a crash on a pruned node with a large cache may replay thousands of blocks at startup, as master after a long flush interval; gain: about half the coin writes on a pruned sync (4.10).
- A deep reorganisation's memory (D3): a step that disconnected blocks checks the coins cache only in `FinishConnectStep()`, so its connects can take the tier over the critical budget by about the depth times one block's changes; master checks per block, but also holds a reorganisation's new branch in `connected_blocks` outside `-dbcache` until the block that passes the old tip's work (its step returns there, `ActivateBestChainStep()`), so about the same depth (corrected 2026-11-18 against e211dd0186; this said master held the whole new branch). The lever (option B, which the maintainer liked): in a step that disconnected blocks, end the step after a connected block that leaves the cache critical, and let the next step carry on along the branch.
- The kernel's validation callbacks may run on the effects executor's thread and must not call back into the chainstate manager (V8, option B: the kernel interface is experimental, a documented break is fine); one sentence in `bitcoinkernel.h`, no code change.

The reach of all of it: the three commits of pass 3 were measured on the regtest heavy chain only, level or better against the 40 commits (7.7); no mainnet or real-network run of them exists, and nothing above 16 cores (5.5).

## 6. How to measure

### 6.1 Method

The maintainer: "I just don't believe that this is the ceiling already." And: "you are allowed to write your own instrumentation and benchmarks, as long as they don't take long and don't slow you down. Are you really sure you need all these probes?" Kept from this: a reference on the same box (master on the harness chain), counts of work per transaction and not only timers, and trying the change itself on a throwaway branch; kept when it beats the noise of alternating runs, dropped otherwise.

Throughput in the window stretch is threads times the share on CPU divided by the CPU a transaction costs; a limit on one factor is not a ceiling.

### 6.2 A run on the maintainer's machine

Mainnet `-reindex-chainstate` to height 975073, `-dbcache=30000` (no lag run happens during the connect at that size: every coin, 166 million changes, is still unwritten at the stop height), 32 connect workers, `-par=16`, `-debug=coindb`, 32 vcores. Every run command carries `-disablewallet`: a loaded wallet past its birthday does per-transaction work on `BlockConnected` during a reindex and filled the validation-interface queue (hundreds of seconds of publisher wait in two runs). Bench per-block figures divide by windowed blocks. `-debug=bench` slows the publisher; sampled runs say so.

### 6.3 The harness

Scripts are in `/work/utxo-partial-order-harness/` (README). Chains D and DX are kept there too (`chains/`: the builder's datadir and `tip.txt`); the other chains regenerate from their scripts. Datadirs in use and binary snapshots live in a session's temporary directory and go with it; their numbers are in these notes. Marks and the standing caveat are in the header; in particular the harness chain's blocks are all allocation and its store is small, so its ratio for anything about a block's memory is an upper bound, not a prediction.

Settings that every harness run needs:

- The baseline is branch `utxo-partial-order-baseline` (326374edc0): master e211dd0186, the current cut's base, plus one probe commit that adds the series' `-test=bip30_off` to regtest, never for upstream. #### The block file read-ahead (commit 46, 14 November)

The maintainer, on the dip between 600,000 and 800,000 (7.1): "Just try out the block reads and the serial publisher", memory growth being accepted as a cost. No code gave the operating system a read-ahead hint, and each block is read by its worker with an open, an 8 byte read and the block's read. The connector thread now asks for the block files up to four ahead of the one a staged block is in (`BlockManager::ReadAheadBlockFile()`, `posix_fadvise(WILLNEED)`), as a front task on the connect pool. Linux (5.15 on the dev box, read_ahead_kb 128) cuts one request down to its read-ahead window: one call for a 127 MiB file cached 320 pages, the same file in 128 KiB steps was cached whole within 0.29 s for 43 ms of calls, so the function steps.

Harness (`ab3.py`, `EVICT=1` drops chain D's block files from the page cache before each run, 16 workers, four rounds): read wall 6.82 ms a block against 9.07 (cached: 6.73), 526.6 against 496.9 blocks/s (1.06x, ranges apart); cached, three rounds, 521.0 against 511.8, inside the spread. The maintainer then asked whether it works at all, blocks being stored in arrival order, not by height (the harness chain is stored by height, so this was not exercised). The files are asked for in file order, each once, up to four above the highest file a staged block was in; as first committed, a block whose file lay more than four above the mark made the files in between be skipped, which a late arrival (up to the download window of 1024 blocks, about a dozen files) does. Folded fix: the request starts at the mark, at most sixteen files below the block (`READ_AHEAD_BEHIND_FILES`) (the state before it: 0d2e4e1f8c). What remains by design: the file of a late arrival is asked for only when that block is staged, so that one block is read cold. The publisher's two trials (pool size, worker priority) are in 5.2 and showed nothing on the harness.

### 7.4 Where the workers' idle time went

What holds by construction: a store entry is made by one thread and released by another, since the block that creates an output and the block that spends it run on different workers. Allocator literature names remote frees as the hard case (10). glibc's per-thread cache takes seven objects per size (`glibc.malloc.tcache_count`) and serves a free from another thread under the allocating thread's arena lock. The idle time was a sum of microsecond gaps whose cost follows the number of sleeps, not their length (a park costs 7 to 10 microseconds).

Thread counters per worker on the maintainer's machine (32 workers, before the depot) showed two regimes: a baseline of about 10% blocked in parks of about 8 µs where the set does not grow, and 7 to 12 points more in parks of about 27 µs where it grows. The continuation was about half of all off-CPU time (4.6 of 9.0 ms a block at 550k to 800k, 7.6 of 16.1 ms at 800k to 950k).

The idle probe (thread states, system calls and park stacks of four workers), per connect worker before and after the depot:

|---|---|---|---|---|
| on a CPU | 79.9% | 86.8% | 77.0% | 89.3% |
| waiting for a core | 7.4% | 6.7% | 5.4% | 8.8% |
| asleep | 12.8% | 6.5% | 17.5% | 1.9% |
| parks a second | 9,900 | 2,470 | 11,900 | 3,080 |
| futex, share of wall | 17 to 20% | 6 to 7.5% | 20 to 26% | 3.7 to 4.8% |

Before: 83 to 88% of all parks were the glibc arena lock in free or malloc: the free of a map cell beyond the kept bound in `Map::erase` under the shard mutex (58 to 63%, most from `RunContinuation`), the old `CTxUndo` coin vectors in `SettleUndo` (10 to 16%), the destruction of a `CBlock` in the bins (7 to 9%). After, parks left late: map cell free past the depot 63% (about 1,950 a second, before 6,900), undo vectors in `SettleUndo` 10%, witness byte vectors 5%, block destruction 3%, shard mutex 2%, block file read 2%. Further trials, none on the series:

- The batched fetch for a continuation (18 lines): cont wall 0.91x, cont CPU 0.92x, block rate equal on the harness.
- The read phase. `BlockManager::ReadBlock` on the worker: open the file, a zeroed buffer, the read with the xor, `DeserializeBlock` (txid and wtxid hashed from the bytes by the worker, `make_shared` `CTransaction`), header hash and proof of work; 28% of late worker CPU then (14.1 ms a block). The allocation share is the layout of `CTransaction` and has no small fix.
- Input coins looked up once and passed by position (branch `utxo-partial-order-span`, two commits on 5d49673c35, 157 lines). `CCoinsViewCache::AccessInputs(tx, coins)` looks each input's coin up once and returns pointers in input order; `Consensus::CheckTxInputs`, `GetP2SHSigOpCount`, `GetTransactionSigOpCost` and `CheckInputScripts` get an overload taking those coins and the view-taking forms call it. The maintainer's objection holds: a free on a thread other than the allocating one queues for that arena's lock, the record is already a cross-thread free, and only a free by the worker that built the record avoids it, while a continuation may run elsewhere. Revisit when a machine shows the publisher as the bound.

The fall from 8 to 16 workers on chain E is not the window width (no trend from 8 to 64), not the BIP30 lookups (they cost at four workers, nothing at eight) and not the markers (off: every rate rises, the fall stays between 12 and 16). It is more runnable threads than cores: a chain E block is so small that the publisher (50 to 90 µs a block), the scheduler thread with the validation callbacks (about 23 µs, three sleeps a block) and the effects executor (about 12 µs) are each about as busy as a worker and have no core of their own. Confined to 8 cores the peak is at 6 workers (12060 to 13200 against 8970 to 9640 at 8); on 16 cores 13430 to 15160 at 12 against 10450 to 12090 at 16. With work in the blocks it does not carry over: chain D 397-409 / 442-464 / 444-475 / 431-496 at 12 / 14 / 15 / 16 workers. The default of one thread a core is right where the time goes.

Open and unsampled: one block with far more script work than its neighbours holds the window while the other workers run out of blocks; master spreads one block's scripts over all threads and has no such case.

### 7.6 The design review of 2026-11-13

Asked: go over the whole design again, interrogate the memory and parallelism tradeoffs and pruning, and say whether a different design reaches equal or better performance with every constraint intact. Seven passes: constraints (section 2), inventory (4.1), memory, parallelism, pruning, alternatives, synthesis (5.1, 5.2). On the maintainer's word the passes stayed on the design level: no measurement, no code. Only what the verdicts of 5.1 and 5.2 rest on is kept.

**Memory.** Outside `-dbcache`, in MiB at 2 / 16 threads, late mainnet blocks taken at 5.4 MB in memory (I): the window 22 / 56 at a 450 MiB cache, 128 at 1 GiB, 173 with a large cache (4.5); the block cache 128 whatever the cache; receive tasks 6 / 90; block bins 22 / up to 173, counted by no budget and the weakest figure; kept-node lists 0.5 / 4; the depot 8; the hash pool 3 / 12 (since removed); the undo of published blocks until the effects thread wrote it, at most 64 MiB serialised. Sum about 190 MiB at 2 threads, about 470 MiB at 16 with a 450 MiB cache and 540 MiB at 1 GiB. A flush worker adds its shard (moved, not copied) and one batch.

- At the small default the memory outside the budget is of the size of the budget (I); the harness never showed it because its blocks are small. This is the largest open point against C4 and a matter of accounting, not mechanism. The thread default multiplies receive tasks, bins and kept lists by the core count without regard to memory. The low-end case, four cores with 4 GB, sums to about 220 MiB (I); never measured.
- The one byte budget of 5.1, derived from `-dbcache` with `-blockcache` as its override, would replace four bounds and take the thread count out of the memory question; its price is the block cache's gain on the network path (row 6 of 4.1) where the budget is small.
- Per coin 147 B on a real run against 138 B for master, about 6% fewer coins for the same bytes (I). The cell is 128 bytes and 144 from glibc; a hand-laid cell of 112 would move the accounting and needs one link removed. Parked on the maintainer's agreement for the low-end phase.
- Resident memory on the maintainer's machine is the highest cache size plus about 2 GiB (freed cells stay with the allocator, about 0.5 GiB is the window). The maintainer: "totally fine then".
- The batch (peak resident memory on chain M on the network harness, branch and master, at 450 MiB, 1 GiB and 8 GiB with 2 and 16 threads) ran: 7.7.

**Parallelism.** Beside the connect pool at one thread a core, the helpers (hash pool, effects, connector, handler, socket, the database's background thread) are nearly idle by measurement, except the socket thread at a high link rate and the database's background thread at the prune ceiling. So the pool is oversubscribed by one to two busy threads; that costs rate only on blocks of a few dozen transactions (7.4), and the default stays. Of the four factors for the late connect, the share on CPU is at 89 to 92% (at most about 1.1x left), CPU per transaction is in 7.3, and the serial parts are the flush, the publisher's own time (7.1) and the blocks above assumevalid. On a real sync the connect is not the bound (7.5); on two to four cores CPU per transaction counts, not width.

- The connector thread stays (it lets the handler and the receive tasks hand blocks on without activating); the flush helpers stay at up to four; the window cap of 64 stays (only machines above 32 cores see it). The hash pool and the effects thread were measured since (7.7); the pool size and the retry lock are in 5.2.
- Deferral: 310 million transactions deferred and no conflict on mainnet, about a quarter of all (I), each costing one database read that finds nothing; the two cheaper forms are in 5.2.
- The low end with a binding cache (6.3) was never profiled: the least understood part of the parallel design.

**Pruning.** No pruned sync of the series was measured in a way that isolates the node.

- Two mechanisms keep the written head above what pruning may delete: the lag ceiling (4.10), and the prune flush, which before a file is unlinked writes out past the last prunable block. The second is sufficient where it holds; no crash sequence could be constructed in which the ceiling saves a node the prune flush does not. Not closed: that every path that unlinks files goes through that flush (the two automatic finders, the manual prune RPC, the pin), and the replay length after a crash.
- With the ceiling a pruned node writes every coin that lives longer than about 129 to 256 blocks. Without it a prune flush writes only up to the prune height, at least 288 blocks below the tip, and with 79% of spends under a day old most coins of the stretch never reach the database, where master writes every dirty coin up to the tip at every prune event (it keeps its cache: `Sync()` at a prune flush on e211dd0186; this passage said it emptied the cache, corrected 2026-11-18). On paper the series without the ceiling writes less than master on a pruned sync and with it more (I): the largest expected low-end gain of the review, and a removal.
- `EvictClean` in one piece silences the socket thread (7.5); a bounded amount per block on the confirming worker would spread it.
- The batch (a pruned sync against master on the network harness with files deleted) ran, and the reading of the prune paths found two gaps the ceiling hid; the ceiling is gone: 4.10, 7.7.

**Alternatives.** Inside the design, every component is "keep" except those in 5.1 and 5.2. Two comparisons carry the answer:

- Master's cache with inputs fetched in parallel ahead of a serial apply is worse on a reindex by measurement (7.3). On a real sync it is not ruled out, since there the delivery is the bound and master's connect rate on real hardware is unknown (5.2).
- The independent design. A fresh agent designed from the goal, the constraints and seven facts, without the series (its memory index carried one-line summaries of the branch, so agreement is weak evidence). It agrees on the receive side, the key-range shards with sorted batches and memory inside `-dbcache`. It differs at the centre: no deferral. Its window is a batch of consecutive blocks; each block emits its creations and spends per shard in block order, one task per shard applies them in order, and the checks run per block in parallel on the coins found. That has no missing input, no continuation, no record of an open block and no retry rule, at the price of a barrier at each window, every surviving coin inserted twice and cs_main held through the ordered phase. It also writes the database only between windows by master's flush, which drops the low-end write-out logic the maintainer said to keep. Verdict: no cheaper way to the same place for the low end; deferral is one of two ways to order the inputs and the other is simpler, but changing over would rewrite the series' centre, and the BIP30 gap it would have closed by construction is closed (4.6).

The external designs (sources in 10; figures self-reported), each with the constraint it breaks: Utreexo and UHS need a protocol change, against receive-only; SwiftSync needs a hints file, a new input; Libbitcoin gives up pruning and the small machine; Hornet (48 B a coin against 147 B here, in a compact index over an append-only file) gives up `-dbcache` and the small machine; Core issue 36476 adds trust in the assumevalid range. None reaches the goal inside the constraints.

Ruben Somsen, "Out-of-Order Validation & The Single Spend Check" (gist RubenSomsen/21c45b1c57448881ce5007d884fb3f21, 2026, a summary of the 2140 Bitcoin Consensus Code Week, given by the maintainer on 19 November), read against the series:

- Its logical design (headers first, blocks downloaded in order within a moving window, integrity checked on arrival, transactions validated in any order once a gap-free run of blocks back to genesis is in) is the series' shape already: the request window, the off-lock check and store of a received block (commit 8), and the connect window validating blocks beside each other once they follow the tip without a gap. Its argument for not going further (validation is bound by bandwidth or by hardware, and waiting for the blocks below costs nothing either way) is the series' own reason for a window of a fixed width rather than validation in arbitrary order.
- Double spends: it optimises for their absence and orders only when one occurs, the series' choice too: blocks apply out of order, the store tells two spends of a coin apart by height (the lower stands, the higher block gets a conflict), and a conflict sends the block back to be connected alone, which is its "another pass to find the double spend if it occurred".
- The single spend check (a spent bit per output, set without reading, spends counted against inputs; or unspent bits against outputs minus inputs) is wait-free but needs a set that keeps spent outputs, and the document itself grants that pruning spent outputs, which the series must do for the small machine (C4), loses most of its benefit, and that exclusive access by compare-and-swap or sharded locks is fine in practice. The series' store is the conventional kind (256 shards, a lock each); the workers' parks were measured as mostly the allocator's lock, not the shards' (7.4: 83 to 88% the glibc arena before the depot), so a wait-free set would buy little here. What carries over is the counting as a cheap global check, which is P10 (5.4, a salted aggregate of creations minus spends as a test oracle; not built).
- Adding each block's outputs to a set on arrival, before validation, is the window matching trial of 19 November (4.12): built, correct, and not faster on the harness, because deferral was already cheap.
- Its output-caching figures (about a third of outputs spent in their own block, and of the rest 9 / 31 / 66 / 83% within 1 / 6 / 144 / 2016 blocks, from mainnet.observer) are of the same shape as the spend ages recorded here (7.5: 23% in the same block, 52% within an hour, 79% within a day; counted differently). They support the lag keeping young coins in memory; nothing new to build.
- Separating signature checks from the rest of the script check, for batch or GPU verification, is the one direction the series has not touched. It matters only above assumevalid, where scripts run (and at the tip, where the signature cache already holds most of them, C3); the series' measurements are below it. A possible later step, outside the current goal; not proposed.
- SwiftSync, compared again: its hints file is a new input, against C2 ("no hints") and the receive-only rule, as recorded above; the document's case that the hints' source is trusted only against wasted time, not for validity, does not change that constraint.

Conclusion: the document describes the design the series already is, by a different road; its novel part, the single spend check, does not fit a store that prunes, and its counting survives only as the P10 oracle. Nothing in it calls for a change to the series.

Take-aways from this run (the analysis of 19 November; measured where a figure is given, reasoning otherwise):

- **What it shows.** The series syncs a pruned node through the whole chain, the 2023 to 2025 blocks included, with a clean stop and no fault. In absolute terms it was fast for the hardware: about 700 GB in 2:28, about 80 MB/s on average, at the network thread's v2 ceiling (about 210 MB/s) in its good stretches. What it does not show: the series' share of that speed. There was no master run on the same host, and with real peers one would be blurred by peer luck as on signet; a ratio needs the maintainer's machine or a harness run.
- **The cache must leave the chainstate room in the page cache.** On disk the UTXO set is compact (13 GB here at 975,073); in the coins cache each coin takes a larger structure, so a page cache that holds the chainstate files covers more coins per GB than the coins cache. With `-dbcache=16000` on 30.5 GiB, about 6.7 GB of page cache was left, and misses became random disk reads at about 61 KB each (readahead, inferred): 700 MB/s read for about 30 MB/s of blocks, 8.6 blocks/s. At 6000 the reads fell to 1.6 MB/s. The rule of thumb that follows: leave the chainstate's size on disk, plus room for the block files the window reads back, in the page cache, and give the rest to `-dbcache`. Not series-specific; master with the same cache hits the same wall. The exact break-even point was not tested.
- **At a small prune target pruning becomes a continuous write-out.** The series deletes a file only below a coins head on disk (C5, D1), so at `-prune=550` every prune event forced a run to a few hundred blocks below the tip, about 200 write-out lines a minute, and the single write-out executor ran saturated while the connect workers idled (the first attempt, deleted). At 20 GB the events were rare but large.
- **Master's IBD prune buffer turns the bounded prune run into a whole-cache write.** During IBD `FindFilesToPrune` adds 1 MB per remaining block to its buffer, so each event prunes to just below the tip. That policy fits master, which flushes its whole cache at every prune event whatever it deletes; in the series a prune run writes only the changes at or below the height pruned to, so pruning by need (just enough to get a margin under the target) would write only the oldest changes per event. Spend ages (7.5: 79% of coins spent within about 144 blocks) suggest the total written would change little; the gain would be many short stalls instead of few long ones. Not built, not measured.
- **The stall is the connector's wait for the run, not the write itself.** A run started in the publication hold is waited for before the next block is published (the store's run must not see newly confirmed changes), so each prune event paused publication for about a minute from 2018 on. Pruning itself needs only that the files wait for the run (commit 15 already chooses them later). Letting runs overlap publication (5.2, the low-end lever) is the way to remove these stalls and the memory runs' alike, but it is not simple: 4.4 records that a run overlapping publication is wrong as such, and that the simple rule (cap the settled height below any dirty entry changed during the run) would hold the written height almost still, since published blocks spend coins of every age. A prune run would need its own form of it, a design question for the low-end phase.
- **The peers limit early on through window and round trip.** With every request slot full (130 to 155 blocks in flight), two peers with 25 and 114 ms pings delivered 60% of the data and peers with 0.4 to 2 s pings 4 to 29 MB/s each. A larger request window for peers that deliver quickly, beside the existing rule for slow ones, would be the receive-side lever; noted, not pursued.
- **v2 decryption on the single network thread binds on a real network too:** 92% of a core at 213 MB/s here, as in the harness (7.7).
- **`getpeerinfo` did not answer within 30 s under IBD load**, once; worth a look only if it recurs.
- **HDD setups (reasoning, untested).** The series' parallel coin reads across a window give a disk a deep queue it can reorder, the syncs left `cs_main`, and the 50% write-out share wrote 26% fewer changes than master's write-everything in the maintainer's runs of 16 November (12 runs against 9, the connector stopped 28.0 against 39.4 s); all of that should help on an HDD. The connector's wait for each run grows with disk latency and is the weak point there, a pruned HDD node with a small cache the worst case; the best kept share may sit below 50% on an HDD (each run's syncs cost more). The gain over master is expected to be real but smaller than on an SSD, since validation's spread over cores helps little against seeks. Settled only by a `-reindex-chainstate` with the chainstate on an HDD, series against master, and the share curve repeated there.

### 7.9 The memory profile of 2026-11-18 (the maintainer's machine, the machines series at 74e8e1db9a)

Two collections with `/work/patches/utxo-partial-order-memprofile.sh` on a `-reindex-chainstate` run (16 cores, 32 threads, `-dbcache=30000 -prevoutfetchthreads=32`), sampled late in the run for ten seconds: one on glibc (at height 841,015), one with jemalloc preloaded (at height 856,366). The preload is a measuring aid only; no allocator swap goes on the series (section 2), and the run time with it is not recorded on the maintainer's word. The two samples are 15,000 blocks apart, so small differences between them mean nothing. `-par` differed between the runs and is irrelevant below assumevalid.

Readings:

- The processors are fully occupied: all 32 connect workers carry about the same share. The run is memory-bound: 0.55 instructions per cycle on glibc, 0.65 with jemalloc, against 2.26 measured above assumevalid.
- The allocator is about 23% of CPU on glibc (frees about 17 points, mostly `_int_free_merge_chunk`) and about 3.4% with jemalloc. Instructions in ten seconds rose from 766 to 898 billion, so removing the allocator's cost altogether is worth about 1.09x: the ceiling for allocation work in code. CPU saved converts at about half, the rest is absorbed by the store's loads. The call stacks stop at the libc boundary, so the allocating call sites are not identified.
- The coin hash (`SaltedCoinsCacheHasher`) is 11 to 12% of CPU in both runs, pure computation. `memset` 2 to 3%, `SerializeTransaction<SizeComputer>` 2 to 3%, `_copy_to_iter` 1.6 to 2.6%.
- Cache misses are the same in both runs (6.4 billion in ten seconds) although everything else changed.
- Far loads (c2c header, jemalloc run): of the loads that leave a core's own caches, 66% are served from main memory, 18% from a line modified in another core's cache, 17% from the shared L3. The table of contended lines came out empty.
- Load latency by source line (jemalloc run): about 32% of the weight sits on the store's prefetch instructions (`Map::Ahead()`: 16.1% in the `ApplyBatch()` batch, 11.1% in `FetchFor()`, 4.7% the write prefetch of list neighbours) and about 3% on the probes that follow them (the key compare in `find()` inside `ApplyBatch()` is 0.14%). The prefetches are timely: neither late nor missing.
- The other waits are scattered: the block-file copy out of the page cache 19.4% in many short loads; `ConfirmBlock()` reading the change record other workers wrote 4.8%; `BlockApplyView::Prefetch()` collecting outpoints 4.1%; `ApplyBatch()` outside the batch 6.8%; `AnnounceCreates()` about 2.8%; `ApplyChanges()` 1.5%; `BlockMerkleRoot()` 1.3%. No single large target.

Open, not verified:

- Settled 2026-11-19 from the same two collections' CPU recordings (perf record, cycles, 5 s): the two batch lambdas carry 19.9% and 13.1% of the load-latency weight on glibc but 1.98% and 1.67% of the cycles, and 20.9% and 11.9% against 3.87% and 3.42% with jemalloc. A thread waiting on a load accrues cycle samples there, so the weight on the prefetch lines is their fill latency, overlapped, not waiting: the store's misses are hidden. The cycles go to computation and many small items instead (the coin hash 11.6%, `BlockApplyView::ApplyChanges()` 5.2%, SHA-256 3.6%, `memset` 3.1%, frees 2.8%, the kernel's block-file copy 2.6%, jemalloc collection).
- Whether 32 threads saturate the memory system: the maintainer's runs of 18 November with 16 and 24 connect threads (7.1) answer as far as one machine can: 12:27.55 and 11:46.05 against 11:36.26 at 32, so the threads beyond 16 buy 7% of wall time for 1.79x the CPU time, and those beyond 24 1.4%. The processor has 16 cores and 32 hardware threads, so the result does not separate the memory system from a core's shared resources (two workers per core above 16); either way the parallelism past one worker per core is nearly spent there, and the remaining time is the work per coin. (These runs were given on 18 November and recorded only on 19 November; until then this point read: not answerable from these collections, both at 32 threads.) A rough bound: 6.4 billion cache misses in 10 s, about 41 GB/s if each is a 64-byte line, a large share of dual-channel DDR5 in practice but not clearly its limit (the counter's meaning on this processor and the write traffic not checked). A run at `-prevoutfetchthreads=16` answers it.
- Why a prefetch weighs ten to fourteen times a block-copy load. Either the memory system is saturated by 32 threads (which would also explain the equal miss counts, and harness gains that ran flat on this machine), or a core queues the burst `PrefetchAll()` issues behind its limit of outstanding misses, which is harmless while the probes arrive after the data. A run with `-prevoutfetchthreads=16` tests the first; a flat result does not tell a per-core from a whole-system limit, since two hardware threads share a core's miss capacity.

Candidates named, none measured or decided: a cheaper coin hash (the upstream SipHash work is to be read first), the block read's zero-fill and copy, the second walk over transactions for their size. Pacing the prefetches is not indicated by this evidence.

### 8.3 The two defects as found

Both closed (4.5, 4.6); kept for the mechanism.

- The BIP30 gap. A window block's BIP30 check did not see a coin that was never written and that a higher open block had spent, because the spend erased the entry at apply and an applier's miss does not scan the open blocks' records. It can only matter where BIP30 is enforced inside the window and a duplicate transaction can be built: a mainnet fork without the BIP34 block above height 227,931, regtest with `-testactivationheight=bip34@N` for N above 1, and mainnet from height 1,983,702; not on the real mainnet chain today.
- Exceptions on the pool. `RunContinuation` caught `std::logic_error` and `std::runtime_error` and had no guard like `RunConnectTask`'s. `ThreadPool::Submit` wraps a task in a packaged task, so any other exception was stored in a future nobody reads, `finished` was never set and the connecting thread waited for ever; the same wrapping meant an allocation failure on a pool worker did not terminate the node.

## 10. Sources

The sources something was taken from, and those compared and not taken. The first research round's own list, with links, is the "Sources" part of `/work/utxo-architecture-research.md`. "M" marks a source the maintainer gave.

- The Delving thread "Libbitcoin for Core people" (delvingbitcoin.org/t/libbitcoin-for-core-people/1222) (M): post 34, the link the maintainer gave, is evoskuil's (existence and spentness need the block order, script validation only a partial order); sipa's reply, post 36, has the "negative UTXO" entry that cancels when the output arrives. Together the origin of the window and deferral (section 1).
- Libbitcoin's v4 database design: validation split from confirmation.
- Hornet Node, UTXO(1): a store written by age at a steady rate with nothing emptied (the young tier and lag runs).
- purpleKarrot, "Towards a Side-Effect Free Validation Library", parts 1 to 3 (purplekarrot.net/blog/bitcoin-validation-library-3.html) (M): the pure core and the script cache as a sequential, a parallel and a sequential phase; recorded in `/work/validation-refactor-plan.md`.
- Bitcoin Core PRs: 31645 (`-dbbatchsize`) for the size of runs and flush batches; 31875 (sorted batches) for the key-ordered flush (4.8); 25325 (the pool resource for the coins cache) as the precedent behind the pool-per-shard trial (7.3).
- Benchcoin PR 201 with the artifact of run 42992592996 (M), and a friend's mainnet sync log: 7.5. A friend's review report (gist willcl-ark/9fe44851f113830b361e6a1ebbddf709) (M): 4.11.
- Dice, "Malthusian Locks" (arXiv 1511.06035), and Karlin et al. on competitive spinning: a lock that always blocks does poorly for short holds, which is why the shard lock retries before it blocks (T3 would undo that and is held).
- BatchIt (ISMM 2024), the snmalloc and mimalloc papers, the glibc documentation: a free on a thread other than the allocating one is the hard case, and the answer is to hand objects back to their owner in batches (4.3).
- Lozi et al., "The Linux Scheduler: a Decade of Wasted Cores", and Gregg, "CPU Utilization is Wrong": read waiting for a core and sleeping apart from the on-CPU share (6.1).
- Ruben Somsen, "Out-of-Order Validation & The Single Spend Check" (gist RubenSomsen/21c45b1c57448881ce5007d884fb3f21) (M): read against the series in 7.6; its double-spend handling matches the store's conflict and retry rule, its single spend check needs a store that keeps spent outputs.
- Compared and not taken (7.6): UHS (Cory Fields, bitcoin-dev May 2018) (M), SwiftSync (gist RubenSomsen/a61a37d14182ccd78760e477c78133cd, Core PR 34004), Utreexo (M), Core issue 36476, DORA and Seastar (threads bound to data, the shape of the independent design).
